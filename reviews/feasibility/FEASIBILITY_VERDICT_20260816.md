## 1. 최종 판정

**프로젝트 방향과 “수요 확인 후 자동화” 게이트는 현실적이다. 그러나 현재 문서의 `Track A 7주 + Track B 4주` 일정은 현실적인 기준 일정이 아니다.**

현재 11주는 재작업, 외부 승인 대기, 캠페인 관측 창, 첫 실전 PR 실패를 거의 허용하지 않는 낙관 일정이다. 주 15~20시간을 유지한다면 다음처럼 잡아야 한다.

| 시나리오 | 현실적인 종료 시점 | 의미 |
|---|---:|---|
| 수요 또는 자동화 가치 부족 | **10주 전후** | Track A 종료 후 정상 `NO_GO` |
| 최소 CLI만 구현 | **15~17주 전후** | 3개 절단안을 적용한 Lean GO |
| 현재 수용 범위를 대부분 유지 | **18~19주 전후** | Plan-complete GO |

따라서 **사업·제품 실험으로는 GO, 현재 일정 약속으로는 NO_GO, 일정과 범위를 고친 뒤 실행은 조건부 GO**다.

## 3. 일정 판정

### 3.1 현재 계획 그대로

일정 전문가는 Phase별 작업과 자체 테스트를 분해해 다음처럼 추정했다.

| 범위 | 낙관 | 기준 | 비관 | 현재 계획 |
|---|---:|---:|---:|---:|
| Track A | 55h | **96h** | 160h | 7주 |
| Track B | 92h | **145h** | 217h | 4주 |
| 전체 | 147h | **241h** | 377h | 11주 |

- Track A는 작업시간보다 캠페인 피드백·관측과 Sponsors 심사 같은 캘린더 대기가 문제다.
- Track B는 Phase 7 구현·테스트와 Phase 8 결함 수정 시간이 계획보다 크게 빠져 있다.
- 현재 11주 달성 확률 `3~5%`는 전문가의 3점 추정 결과이며, 통계적 보장은 아니다.

### 3.2 두 전문가의 Track B 추정 차이 해석

일정 전문가는 현재 수용 범위를 유지한 완료 비용을 **128~145시간, 8~9주**로 보았다. 엔지니어링 전문가는 아래 절단을 적용한 최소 코어를 **16 집중 개발일, 약 80시간**으로 보았다.

1. 라이선스 자동 분류기 → 운영자 승인 파일 + 해시 기반 `STALE`
2. LLM 초안 생성 → 결정론적 템플릿 우선, LLM은 실측 후 옵션화
3. ETag 캐시 → 삭제, Octokit throttling/retry 사용

두 결과는 모순이 아니다. **80시간은 최소 구현 공수이고, 128~145시간은 문서·운영·추가 채널·재작업까지 포함한 계획 완료 공수**다.

주 15~20시간 기준으로 Track B의 약속은 다음처럼 나누는 것이 안전하다.

| 약속 수준 | 권고 일정 |
|---|---:|
| Lean CLI 구현 목표 | **5~6주** |
| 현재 QA·운영 범위까지 완료 | **8~9주** |
| 4주 | 주 20시간, 3개 절단, 결함 수정 최소일 때만 가능한 스트레치 목표 |

## 4. 실험 설계에서 반드시 바꿀 항목

### 4.1 단일 GO를 세 판정으로 분리

| 판정 | 질문 | Track B 영향 |
|---|---|---|
| `DEMAND_*` | 제3자가 실제로 실행·의존했는가 | 수요 유무 판단 |
| `LAUNCH_*` | 다음 게시를 해도 되는가 | 채널·평판 안전성 판단 |
| `AUTO_*` | 반복 기계 작업이 CLI 유지비보다 큰가 | `AUTO_CLI`일 때만 Track B 시작 |

인정 수요 신호는 실행 로그가 있는 Issue/Discussion, 유효 PR, 활동이 있는 Fork, 설치 후 경험이 담긴 외부 글처럼 **실행 증거가 있는 신호**로 제한한다. Star, 빈 Fork, referrer, 후원 클릭은 보조 지표로만 기록한다.

### 4.2 캠페인 관측 창 수정

- 캠페인 간격: 24시간 → **최소 72시간, 권장 7일**
- 최종 판정: 마지막 게시 후 **14일 관측**
- GitHub Traffic: W7 일회 조회가 아니라 **W3부터 매일 저장**
- referrer 1개: GO 조건에서 제거하고 강한·약한·귀속 불가로 기록
- Show HN: 기본 3차 캠페인이 아니라 별도 준비 게이트

### 4.3 후원 연결 순서

두 전문가 의견을 합치면 순서는 명확하다.

1. **Sponsors 신청과 2FA·지급·세금 준비는 Phase 1 첫날 시작한다.**
2. 승인 대기는 캠페인과 병렬로 흘린다.
3. 공개 `FUNDING.yml`과 README 후원 CTA는 수요 관측 뒤로 미룬다.
4. Show HN을 사용할 경우에는 Show HN 관측이 끝날 때까지 후원 요청을 공개하지 않는다.

즉 **신청은 일찍, 공개는 늦게**가 현실적인 합의안이다.

## 5. 기술 구현에서 반드시 바꿀 항목

### Phase 6 전 필수

1. W3부터 Traffic 일별 스냅샷을 수집한다.
2. W2에 `brief-hash` 헬퍼를 추가해 수동 SHA 작업을 없앤다.
3. 인증은 대상 공개 저장소 1개로 제한한 fine-grained PAT + Octokit으로 고정한다.
4. 라이선스 분류기, 초기 LLM 어댑터, ETag 캐시를 MVP에서 제외한다.
5. 토큰, 정규화, 재시도, PR 상태, `NO_OP`, Traffic 실패 처리 등 누락 계약 12건을 결정 로그에 고정한다.

### 구현 중 필수

- Traffic 권한 실패를 유입 0으로 기록하지 말고 명시적 오류로 종료한다.
- `funding-pr`은 공개 저장소인지 먼저 검사한다.
- Draft PR 멱등성은 열린 PR뿐 아니라 닫힌 PR, 브랜치만 존재, 기존 파일 상이 상태를 처리한다.
- 실제 대상 저장소는 이미 FUNDING 변경이 있을 수 있으므로 쓰기 검증용 공개 테스트 저장소를 별도로 둔다.
- 네트워크 없는 테스트는 `FakeGitHubClient`와 로컬 픽스처로 고정한다.

## 8. 결론

**폐기할 계획은 아니다. 일정 숫자와 판정 방식만 현재보다 보수적으로 바꾸면 실행 가치가 높다.** 특히 수요 검증 전 자동화 금지, 저장소 1개 제한, 자동 게시 제외, Draft PR 사용은 유지해야 한다.

반대로 `7주 + 4주`, 24시간 간격, Traffic 일회 수집, 단일 GO 기준을 유지하면 일정과 의사결정 모두 왜곡될 가능성이 높다. 위 8개 변경을 반영한 뒤 착수하는 것을 권고한다.
