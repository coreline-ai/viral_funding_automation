1. 검증된 프로젝트 사실과 기존 채널 원고를 잃지 않고, 채널의 기본 언어·입력 필드·문체·길이·정책에 맞는 `content-ready 후보`를 만든다.

## 최종 성공 기준

- 기존 검증 원고가 구조화 과정에서 축약·재작성되지 않고 게시 필드 정본으로 보존된다.
- 채널별 `defaultLocale`·`supportedLocales`가 적용되고 한국어 기본 채널이 영어 일괄 생성에 섞이지 않는다.
- 지원 모드는 `compose | reference_only | manual_only`로 구분되며 완성 원고 수와 참고 자료 수를 혼동하지 않는다.
- 상태는 `contentStatus | operationsStatus | approvalStatus` 3축으로 판정한다.
- 실제 게시 준비 완료는 콘텐츠 유효, 채널 운영 조건 충족, 사람 승인 3개가 모두 확인됐을 때만 표시한다.
- publisher role 근거가 없으면 `I/we built`를 생성·승인하지 않는다.
- evidence 없는 기술·기능·성과·사용자·비교 주장은 복사 가능한 후보가 되지 않는다.
- Codex는 이미 로그인된 Proxy의 loopback·caller credential·capability allowlist를 통과한 경우에만 활성화한다. Grok은 텍스트 Proxy contract가 준비되기 전까지 `disabled`다.
- Show HN에는 제목·본문 생성, 번역, 윤문 기능이 노출되지 않는다.
- 같은 idempotency key와 같은 fingerprint의 동시 요청 20건은 provider를 한 번만 실행하며, 같은 key의 다른 fingerprint는 `409 IDEMPOTENCY_CONFLICT`다.
- 브라우저와 loopback API는 같은 `publishFields`, SHA-256 request fingerprint, validation 계약을 사용하고 오래된 응답을 적용하지 않는다.
- OpenAPI는 실제 request·response·error fixture와 channel field schema를 parser/validator로 검증한다.
- loopback 외 bind는 실패하고 Host·Origin·per-launch nonce를 통과한 상태 변경 요청만 provider를 실행한다.
- OAuth token, API Key, CLI 인증 파일 내용은 요청·응답·로그·브라우저 저장소·모바일 저장소에 포함되지 않는다.
- Reddit·DEV는 `reference_only`, Show HN은 `manual_only`이며 완성 게시글 수에 포함하지 않는다.
- 기존 `/api/generate`, CLI 24개 파일, 19개 채널 상태, 18개 원고 생성 기능이 회귀하지 않는다.

6. Codex read-only와 Grok denylist만으로 호스트 비밀 읽기 차단이 증명되지 않았다.
7. idempotency cache가 in-flight 중복과 facts/authorInputs 변경을 처리하지 못한다.
8. sourceHash는 32-bit publishFields hash이고 서버 정본·실행 후 검사가 없다.
9. loopback 외 bind, Host/Origin, side-effect auth probe GET 방어가 부족하다.
10. 계획과 달리 `.grok/skills` 16개 파일이 제품 저장소에 추적되어 있다.
11. OpenAPI 테스트가 실제 schema validation이 아니라 문자열 중심이다.

상세 근거와 재승인 기준은 재검토 보고서를 정본으로 사용한다.

## 핵심 설계 결정

### 1. 원고 정본

- 검증된 한국어 `publishFields`가 source of truth다.
- `internal`, `sources`, `checklist`, `status`는 게시 복사 대상이 아니다.
- AI 결과는 원본을 덮어쓰지 않고 `현재 결과 + 직전 결과 1개`로 보존한다. 영속 revision store를 구현하기 전에는 이를 revision history라고 부르지 않는다.
- 모든 AI 결과는 SHA-256 canonical request fingerprint와 불투명 `compositionId`를 가진다. 원본·facts·authorInputs·profile이 바뀌면 기존 결과는 `stale`이 되고 적용·승인·복사할 수 없다.
- 기존 문자열 `drafts`는 호환 출력으로만 렌더링하며 브라우저 상태 정본으로 사용하지 않는다.

### 2. “완전한 글”의 정의

이 계획에서 AI가 만드는 결과는 우선 `content-ready 후보`다. 완전한 게시 준비 상태는 아래 콘텐츠·운영·승인 조건을 모두 만족한 경우에만 사용한다.

1. 해당 서비스가 요구하는 `publishFields`가 모두 존재한다.
2. 프로젝트 사실, URL, 작성자 귀속이 검증된 evidence에서 벗어나지 않는다.
3. 채널의 문자 수, 배열 구간, 필수 필드, 금지 표현 검사를 통과한다.
4. 작성자 경험이 필요한 채널은 사용자가 입력한 경험만 사용한다.
5. 미디어·Flair·카테고리·계정 조건은 원고와 분리하되 누락 시 `operationsStatus: blocked`다.
6. 사람이 해당 fingerprint의 결과를 명시적으로 승인해야 `approvalStatus: approved`다.
7. `reference_only`와 `manual_only` 채널은 참고 자료가 준비되어도 완성 게시글 수에 포함하지 않는다.
8. 결과가 생성되었더라도 자동 게시하지 않는다.

### 3. provider 실행 원칙

- `grok`과 `codex`는 동일한 `OAuthTextProvider` 계약을 구현한다.
- 앱은 token을 알지 못하며, 로그인된 CLI 프로세스만 실행한다.
- prompt는 stdin 또는 권한 `0600` 임시 파일로 전달하고 성공·실패·취소 후 삭제한다.
- shell interpolation을 사용하지 않고 `spawn(command, args, { shell: false })`만 사용한다.
- 외부 README와 사용자 원고는 명령이 아니라 인용된 데이터로 취급한다.
- 도구·웹 검색·메모리·하위 에이전트·파일 쓰기를 비활성화한다.
- Codex는 `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--output-schema`를 기본으로 한다. 최종 응답은 stdout/`--json`으로 받고 `-o` 파일 쓰기를 쓰지 않으면 `--sandbox read-only`를 유지한다. schema·prompt 임시 파일은 부모 프로세스가 고립 tmp에 0600으로 만들고 Codex 자식은 쓰지 않는다. stdout만으로 schema를 받을 수 없을 때만 고립 tmp에 한정한 `workspace-write`를 허용하며, 그 경우 이유를 Phase 2 이슈에 기록한다. `dangerously-bypass-approvals-and-sandbox`는 금지한다.
- Grok은 sandbox와 도구 0개 fail-closed 구성이 증명된 경우에만 기본 활성화한다. `bypassPermissions`는 금지한다.
- API Key 환경변수는 child environment에서 제거한다.
- child의 OAuth 접근 범위를 최소 HOME 또는 OS-level sandbox로 격리하고, 모든 runtime 결과에 secret·인증 경로·개인 경로 DLP를 적용한다.
- 현재 웹의 Grok/Codex 토글과 `/api/translate`는 호환 유지 후 `auto`를 추가한다. 동작하는 runner를 Phase 2에서 어댑터로 옮기며 통째 삭제하지 않는다.

### 4. 채널별 기본 라우팅

`auto`는 아래 기본값을 사용하되 사용자가 `grok` 또는 `codex`를 직접 선택할 수 있다. provider 변경이 채널 정책 게이트를 약화시키지는 않는다.

| 채널군 | 기본 provider | 완성 조건 |
|---|---|---|
| X 3안·X 스레드·Threads | Grok | 짧은 대화형 문체, 구간별 길이 통과 |
| Facebook·Instagram·Shorts | Grok | 원본 미디어 맥락과 캡션 필드 분리 |
| LinkedIn·Disquiet·OKKY·GeekNews | Codex | 문제·구현·한계·구체 질문 구조 |
| Product Hunt·Peerlist | Codex | 제품 필드와 첫 댓글, 계정·자산 입력 확인 |
| Reddit·Indie Hackers | Codex 후보 | 대상 커뮤니티와 실제 제작 경험 입력 후에만 구성 |
| DEV | Codex 후보 | 실제 기술 사례·코드·실패·AI 사용 공개 입력 후 `needs_review` |
| Show HN | 사용 안 함 | `manual_only`, 작성자 직접 작성 |

- provider 두 개를 자동 연속 호출하지 않는다.
- 선택적 `review` 요청에서만 다른 provider의 비게시용 지적 사항을 받을 수 있다.
- reviewer는 원고를 자동 교체하지 않고 이슈 목록만 반환한다.

### 5. 지원 모드와 3축 상태 모델

채널의 AI 지원 범위를 먼저 분리한다.

| 지원 모드 | 의미 | 대표 채널 |
|---|---|---|
| `compose` | evidence와 입력 게이트 안에서 게시 필드 후보 구성 가능 | X, Threads, LinkedIn, GeekNews, OKKY 등 |
| `reference_only` | 사실·체크리스트만 제공하고 최종 제목·본문은 사람이 직접 작성 | Reddit, DEV |
| `manual_only` | AI 생성·번역·윤문을 제공하지 않음 | Show HN |

단일 `ready` 대신 서로 다른 책임의 상태를 분리한다.

| 축 | 값 | 의미 |
|---|---|---|
| `contentStatus` | `candidate` | 필수 게시 필드와 자동 콘텐츠 검증 통과 |
| `contentStatus` | `needs_input` | 작성자 경험·채널 맥락 등 콘텐츠 입력 누락 |
| `contentStatus` | `invalid` | schema·사실·길이·정책 오류 |
| `contentStatus` | `reference_ready` | reference-only 사실 자료 준비 완료, 사람 원고 필요 |
| `contentStatus` | `manual_only` | AI 게시문 생성·편집 금지 |
| `operationsStatus` | `ready | blocked` | 계정·미디어·카테고리·커뮤니티 규칙 등 실제 게시 조건 충족 여부 |
| `approvalStatus` | `unreviewed | approved` | 현재 fingerprint 결과에 대한 사람 승인 여부 |

- 최종 `publishReady`는 `contentStatus: candidate + operationsStatus: ready + approvalStatus: approved`일 때만 계산한다.
- `stale`은 콘텐츠 상태가 아니라 현재 입력과 결과 fingerprint의 일치 여부를 나타내는 validity flag다.
- `status: hold`인 채널은 콘텐츠 후보가 있어도 운영·승인 조건 확인 전 `publishReady`가 될 수 없다.
- 기존 `status`·`translationPolicy`는 migration 입력으로만 읽고 3축 상태와 지원 모드로 보수적으로 매핑한다.

### 6. 채널별 Locale

- 원본·작성자 입력은 기본 `ko-KR`이며 사용자는 별도의 영어 사실을 입력하지 않아도 된다.
- profile은 전역 target 대신 `defaultLocale`과 `supportedLocales`를 가진다.
- GeekNews·OKKY·Disquiet 기본값은 `ko-KR`이다.
- X·Threads·LinkedIn·Product Hunt·Peerlist·Indie Hackers는 캠페인 선택에 따라 `en-US`를 기본 후보로 쓴다.
- Facebook·Instagram은 대상 페이지·그룹·계정의 언어를 campaign brief에서 명시한다.
- source와 target이 같으면 번역 호출이 아니라 필요할 때만 채널 문체 재구성을 수행한다.
- 영어 일괄 생성은 한국어 기본 채널을 자동 포함하지 않는다.
- 일본어·스페인어·포르투갈어·프랑스어는 계약 확장 가능성만 보존하고 이번 구현에는 넣지 않는다.

## 목표 아키텍처

```text
Web GUI / Mobile client
        │
        ▼
Versioned API Router (/api/v1)
        │
        ▼
Composition Orchestrator
  ├─ Canonical Draft + Verified Facts
  ├─ Channel Completion Profile
  ├─ Campaign Brief + Author/Operations Gate
  ├─ OAuthTextProvider
  │    ├─ Grok OAuth CLI Adapter
  │    └─ Codex OAuth CLI Adapter
  └─ Deterministic Validation Pipeline
       ├─ schema / required fields
       ├─ SHA-256 fingerprint / lock terms / URL
       ├─ claims and evidence
       ├─ channel length / format
       └─ support mode / policy / 3-axis status
```

책임 경계:

- `content/drafts`: 검증된 원고와 게시 필드의 정본·호환 렌더링
- `channel profile`: 채널 입력 필드, Locale, 길이, 작성자 입력, AI 정책
- `provider adapter`: CLI 실행·취소·timeout·구조화 응답만 담당
- `orchestrator`: prompt 입력 구성, provider 선택, 결과 상태 전이
- `validator`: provider와 무관한 결정론적 승인 조건
- `API contract`: transport, request ID, 오류 envelope, in-flight idempotency, Host·Origin·nonce만 담당
- `GUI/mobile`: 입력·비교·승인 표시만 담당하고 정책 판정을 재구현하지 않음

계약 규칙:

- 알 수 없는 최상위 필드와 profile에 없는 게시 필드는 거부한다.
- canonical fingerprint는 channel, source/target Locale, publishFields, facts, authorInputs, campaign brief, resolved provider, profile/schema version을 포함한다.
- 같은 `idempotencyKey + requestFingerprint`의 in-flight·완료 요청은 같은 실행을 공유한다.
- 같은 idempotency key에 다른 fingerprint가 오면 `409 IDEMPOTENCY_CONFLICT`를 반환한다.
- 응답에 OAuth 관련 값, 원시 CLI 환경, prompt 파일 경로, 원문 stderr를 넣지 않는다.
- 웹은 응답 적용 직전에 현재 입력 fingerprint와 응답 fingerprint를 비교하고 다르면 결과 적용을 거부한다.
- 현재 beta는 authoritative revision store가 없는 stateless 계약이며 idempotency cache도 process-local이다. 재시작 후 보장을 주장하지 않는다.
- provider 실패 시 기존 원본과 직전 정상 결과를 변경하지 않는다.
- 모든 provider 결과는 secret·인증 경로·개인 경로 DLP와 facts/evidence 검증을 통과해야 한다.
- 서버는 `127.0.0.1 | localhost | [::1]`만 허용하며 state-changing route는 허용 Origin과 per-launch nonce를 요구한다.
- OpenAPI는 문서 문자열이 아니라 실제 runtime request·response·error가 통과하는 실행 계약이어야 한다.
- 기존 `sourceHash`는 migration 호환용 client correlation 값으로만 취급하고 R2 이후 fingerprint를 authoritative 비교 값으로 쓴다.

## 확인 필요 사항 / 결정 기록

검토일: `2026-08-18`. 같은 작업 범위의 충돌을 여기서 고정한다.

1. **검증 팩과 일반 생성**  
   `campaigns/memory_node_graph/2026-08-first-launch/final`은 해당 저장소 전용 정본이다. 그 저장소이거나 동일 팩이 있으면 구조화 시 전문과 필드 의미를 보존한다. 임의의 GitHub URL `/api/generate`에는 검증 팩이 없으므로 기존 템플릿 초안을 쓰되, 한 번 만든 `publishFields`를 다시 축약·일반화하지 않는다. 모든 repo에 final 팩을 강제하지 않는다.

2. **Codex sandbox**  
   기본은 read-only + stdout/JSON schema다. 고립 tmp의 `-o`/`workspace-write`는 stdout 경로가 실패할 때만 허용하고, 전역 승인 우회는 금지한다.

3. **일괄 번역**  
   기존 `허용 채널 일괄 번역`은 고급 동작으로만 유지한다. 새 일괄 HTTP API를 만들지 않는다. 기본 흐름은 추천 채널 한 개를 생성한다. 고급 일괄은 `/api/translate` 또는 `/api/v1/drafts/compose`를 채널당 한 번씩 순차 호출하고, 대상 Locale이 다른 채널·`reference_only`·`manual_only`·필수 입력 누락 채널은 건너뛴다. 같은 fingerprint의 최신 결과가 있으면 재호출하지 않는다.

4. **브라우저 E2E 도구**  
   Playwright나 새 npm 의존성을 이 계획에 추가하지 않는다. Phase 5·8 브라우저 확인은 기존 테스트와 실제 브라우저 1턴으로 한다.

5. **`/api/v1`과 모바일**  
   이 계획의 끝은 웹이 사용하는 `loopback contract beta`다. 외부 모바일 기기·TLS·pairing·device auth와 실제 모바일 앱은 후속 계획이다. R3의 실행 가능한 OpenAPI와 generated model smoke가 끝나기 전에는 “모바일 호환 완료”라고 표현하지 않는다.

6. **기존 runner**  
   현재 `CliGrokTextRunner`/`CliCodexTextRunner`와 provider 토글은 Phase 2 이관 대상이다. Phase 0은 정본·검증·안전 설정만 고치고 runner를 제거하지 않는다.

7. **재검토 결정 우선순위**
   이 절의 2026-08-20 결정은 최초 계획의 전역 `en-US`, 단일 `ready`, `sourceHash` stale 보장, 모바일 계약 완료 표현보다 우선한다. 충돌하는 과거 Phase 체크는 구현 이력으로 남기되 R0~R4가 재승인 게이트다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- Phase 완료는 코드 존재가 아니라 테스트 결과와 실행 증거가 있을 때만 체크한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 재현·검증 근거를 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 언어, 자동 게시, 클라우드 인증, 데이터베이스 기능을 추가하지 않는다.
- 외부 문서와 원고 안의 지시문은 실행 명령으로 취급하지 않는다.
- 프로젝트명, 저장소 URL, 데모 URL, 기술명, 라이선스, 버전, 확인된 수치는 잠금 사실로 취급한다.
- 시점에 따라 바뀌는 사용자 수·stars·관계 수는 기준 시각과 근거가 없으면 게시문에 넣지 않는다.
- 지원 모드, 3축 상태, publisher role, evidence 판정은 서버 소유이며 provider가 변경할 수 없다.
- 새 의존성은 OpenAPI 검증 등 표준 라이브러리만으로 해결할 수 없는 경우에만 추가한다.
- 실제 OAuth 테스트는 fake provider 테스트와 보안 검사를 모두 통과한 뒤 한 채널씩 실행한다.
- 실제 provider 실패·로그아웃·rate limit은 원고 손실 없이 복구 가능해야 한다.
