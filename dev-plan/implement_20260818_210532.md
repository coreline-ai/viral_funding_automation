이 문서는 기존 채널별 한국어 작업본을 정본으로 유지하면서, 사용자가 선택한 **Grok 또는 Codex의 로그인된 OAuth CLI 세션**으로 서비스별 완성 원고를 구성하고, 웹 GUI와 향후 모바일 앱이 같은 계약을 사용하도록 만드는 개발 범위를 고정한다.

## 개발 목적

1. 검증된 프로젝트 사실과 기존 채널 원고를 잃지 않고, 채널의 실제 입력 필드·문체·길이·정책에 맞는 완성 원고를 만든다.
2. API Key나 토큰 복사 없이 로컬 `grok`·`codex` CLI의 사용자 OAuth 세션만 재사용한다.
3. AI 출력은 그대로 신뢰하지 않고 사실성, 필수 필드, URL, 길이, 정책, 작성자 경험을 결정론적으로 검증한다.
4. 사용자가 한국어로 부족한 경험 정보를 보강하고, 원본과 AI 완성본을 비교한 뒤 최종 승인할 수 있게 한다.
5. 동일한 조합·검증 기능을 웹이 쓰고, 이후 모바일 앱도 붙일 수 있도록 버전이 고정된 로컬 API 계약을 제공한다. 이 계획에 모바일 앱 구현은 넣지 않는다.

## 최종 성공 기준

- 기존 검증 원고가 구조화 과정에서 축약·재작성되지 않고 게시 필드 정본으로 보존된다.
- `auto`, `grok`, `codex` 중 하나를 선택해 허용 채널의 완성 원고를 생성할 수 있다.
- X, LinkedIn, Product Hunt 3개 파일럿 채널이 실제 OAuth 1턴과 결정론적 검증을 통과한다.
- 모든 지원 채널은 `ready`, `needs_review`, `needs_input`, `manual_only` 중 하나로 판정된다.
- `ready`는 “사람이 최종 승인할 수 있는 후보”를 뜻하며 자동 게시 완료를 뜻하지 않는다.
- 작성자 경험이나 채널 맥락이 필요한 원고는 정보가 없으면 절대 `ready`가 되지 않는다.
- Show HN에는 제목·본문 생성, 번역, 윤문 기능이 노출되지 않는다.
- 브라우저와 모바일 API는 동일한 `publishFields`, `sourceHash`, `validation` 계약을 사용한다.
- OAuth token, API Key, CLI 인증 파일 내용은 요청·응답·로그·브라우저 저장소·모바일 저장소에 포함되지 않는다.

## 핵심 설계 결정

### 1. 원고 정본

- 검증된 한국어 `publishFields`가 source of truth다.
- `internal`, `sources`, `checklist`, `status`는 게시 복사 대상이 아니다.
- AI 완성본은 원본을 덮어쓰지 않고 `revision`으로 저장한다.
- 모든 revision은 `sourceHash`를 가진다. 원본이 바뀌면 기존 결과는 `stale`이 되고 복사할 수 없다.
- 기존 문자열 `drafts`는 호환 출력으로만 렌더링하며 브라우저 상태 정본으로 사용하지 않는다.

### 2. “완전한 글”의 정의

완전한 글은 길이가 긴 글이 아니라 아래 조건을 모두 만족한 결과다.

1. 해당 서비스가 요구하는 `publishFields`가 모두 존재한다.
2. 프로젝트 사실과 URL이 검증된 근거에서 벗어나지 않는다.
3. 채널의 문자 수, 배열 구간, 필수 필드, 금지 표현 검사를 통과한다.
4. 작성자 경험이 필요한 채널은 사용자가 입력한 경험만 사용한다.
5. 미디어·Flair·카테고리·계정 조건은 원고와 분리된 `missingInputs` 또는 `internal`로 남는다.
6. 결과가 생성되었더라도 사람 최종 승인을 거치기 전 자동 게시하지 않는다.

### 3. provider 실행 원칙

- `grok`과 `codex`는 동일한 `OAuthTextProvider` 계약을 구현한다.
- 앱은 token을 알지 못하며, 로그인된 CLI 프로세스만 실행한다.
- prompt는 stdin 또는 권한 `0600` 임시 파일로 전달하고 성공·실패·취소 후 삭제한다.
- shell interpolation을 사용하지 않고 `spawn(command, args, { shell: false })`만 사용한다.
- 외부 README와 사용자 원고는 명령이 아니라 인용된 데이터로 취급한다.
- 도구·웹 검색·메모리·하위 에이전트·파일 쓰기를 비활성화한다.
- Codex는 `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--output-schema`를 기본으로 한다. 최종 응답은 stdout/`--json`으로 받고 `-o` 파일 쓰기를 쓰지 않으면 `--sandbox read-only`를 유지한다. schema·prompt 임시 파일은 부모 프로세스가 고립 tmp에 0600으로 만들고 Codex 자식은 쓰지 않는다. stdout만으로 schema를 받을 수 없을 때만 고립 tmp에 한정한 `workspace-write`를 허용하며, 그 경우 이유를 Phase 2 이슈에 기록한다. `dangerously-bypass-approvals-and-sandbox`는 금지한다.
- Grok은 `dontAsk`와 명시적 도구 차단만 허용하고 `bypassPermissions`는 금지한다.
- API Key 환경변수는 child environment에서 제거한다.
- 현재 웹의 Grok/Codex 토글과 `/api/translate`는 호환 유지 후 `auto`를 추가한다. 동작하는 runner를 Phase 2에서 어댑터로 옮기며 통째 삭제하지 않는다.

### 4. 채널별 기본 라우팅

`auto`는 아래 기본값을 사용하되 사용자가 `grok` 또는 `codex`를 직접 선택할 수 있다. provider 변경이 채널 정책 게이트를 약화시키지는 않는다.

| 채널군 | 기본 provider | 완성 조건 |
|---|---|---|
| X 3안·X 스레드·Threads | Grok | 짧은 대화형 문체, 구간별 길이 통과 |
| Facebook·Instagram·Shorts | Grok | 원본 미디어 맥락과 캡션 필드 분리 |
| LinkedIn·Disquiet·OKKY·GeekNews | Codex | 문제·구현·한계·구체 질문 구조 |
| Product Hunt·Peerlist | Codex | 제품 필드와 첫 댓글, 계정·자산 입력 확인 |
| Reddit·Indie Hackers | Codex 후보 | 대상 커뮤니티와 실제 제작 경험 입력 후에만 구성 |
| DEV | Codex 후보 | 실제 기술 사례·코드·실패·AI 사용 공개 입력 후 `needs_review` |
| Show HN | 사용 안 함 | `manual_only`, 작성자 직접 작성 |

- provider 두 개를 자동 연속 호출하지 않는다.
- 선택적 `review` 요청에서만 다른 provider의 비게시용 지적 사항을 받을 수 있다.
- reviewer는 원고를 자동 교체하지 않고 이슈 목록만 반환한다.

### 5. 상태 모델

| 상태 | 의미 | 복사 가능 여부 |
|---|---|---|
| `ready` | 필수 입력과 자동 검증을 통과한 사람 승인 후보 | 사람 확인 후 가능 |
| `needs_review` | 생성은 완료했으나 정책·사실·문체 확인 필요 | 기본 차단 |
| `needs_input` | 작성자 경험, Subreddit, 가격, 자산 등 필수 맥락 누락 | 차단 |
| `manual_only` | AI 생성·윤문을 허용하지 않는 채널 | 차단 |

기존 `status`/`translationPolicy`를 지우지 않고 아래로 매핑한다. 매핑이 정책을 약화시키면 안 된다.

| 기존 | 완성 상태 |
|---|---|
| `translationPolicy: disabled`, Show HN | `manual_only` |
| `translationPolicy: draftOnly` 또는 필수 author input 없음 | `needs_input` |
| `status: hold`이면서 생성은 허용 | 생성 후에도 기본 `needs_review`, 사람 승인 전 복사 차단 |
| `status: draft`/`gate`이고 검증 통과 | 사람 확인 후 `ready` 후보 |

### 6. 1차 Locale

- 원본은 `ko-KR`, 첫 목표는 `en-US`로 고정한다.
- 사용자는 부족한 작성자 경험을 한국어로 입력할 수 있다. 별도의 영어 사실 입력은 요구하지 않는다.
- 일본어·스페인어·포르투갈어·프랑스어는 계약 확장 가능성만 보존하고 이번 구현에는 넣지 않는다.

## 목표 아키텍처

```text
Web GUI / Mobile client
        │
        ▼
Versioned API Router (/api/v1)
        │
        ▼
Composition Orchestrator
  ├─ Canonical Draft + Verified Facts
  ├─ Channel Completion Profile
  ├─ Author Input Gate
  ├─ OAuthTextProvider
  │    ├─ Grok OAuth CLI Adapter
  │    └─ Codex OAuth CLI Adapter
  └─ Deterministic Validation Pipeline
       ├─ schema / required fields
       ├─ sourceHash / lock terms / URL
       ├─ claims and evidence
       ├─ channel length / format
       └─ policy / manual-only gate
```

책임 경계:

- `content/drafts`: 검증된 원고와 게시 필드의 정본·호환 렌더링
- `channel profile`: 채널 입력 필드, Locale, 길이, 작성자 입력, AI 정책
- `provider adapter`: CLI 실행·취소·timeout·구조화 응답만 담당
- `orchestrator`: prompt 입력 구성, provider 선택, 결과 상태 전이
- `validator`: provider와 무관한 결정론적 승인 조건
- `API router`: transport, request ID, 오류 envelope, idempotency만 담당
- `GUI/mobile`: 입력·비교·승인 표시만 담당하고 정책 판정을 재구현하지 않음

### 주요 endpoint

| Method | Endpoint | 역할 |
|---|---|---|
| `GET` | `/api/v1/capabilities` | 지원 schema, Locale, 채널, provider, 정책 조회 |

계약 규칙:

- 알 수 없는 최상위 필드와 profile에 없는 게시 필드는 거부한다.
- `idempotencyKey + sourceHash + channel + provider`가 같은 재시도는 중복 실행을 방지한다.
- 응답에 OAuth 관련 값, 원시 CLI 환경, prompt 파일 경로, 원문 stderr를 넣지 않는다.
- `sourceHash`가 현재 원본과 다르면 `409 SOURCE_STALE`을 반환한다.
- provider 실패 시 기존 원본과 이전 revision은 변경하지 않는다.
- 기본 서버 bind는 계속 `127.0.0.1`이다. 외부 모바일 기기 연결은 후속 보안 릴리스에서 TLS·pairing과 함께 다룬다.

## 확인 필요 사항 / 결정 기록

검토일: `2026-08-18`. 같은 작업 범위의 충돌을 여기서 고정한다.

1. **검증 팩과 일반 생성**  
   `campaigns/memory_node_graph/2026-08-first-launch/final`은 해당 저장소 전용 정본이다. 그 저장소이거나 동일 팩이 있으면 구조화 시 전문과 필드 의미를 보존한다. 임의의 GitHub URL `/api/generate`에는 검증 팩이 없으므로 기존 템플릿 초안을 쓰되, 한 번 만든 `publishFields`를 다시 축약·일반화하지 않는다. 모든 repo에 final 팩을 강제하지 않는다.

2. **Codex sandbox**  
   기본은 read-only + stdout/JSON schema다. 고립 tmp의 `-o`/`workspace-write`는 stdout 경로가 실패할 때만 허용하고, 전역 승인 우회는 금지한다.

3. **일괄 번역**  
   기존 `허용 채널 일괄 번역` 버튼을 유지한다. 새 일괄 HTTP API를 만들지 않는다. Phase 3 이후 이 버튼은 `/api/translate` 또는 `/api/v1/drafts/compose`를 채널당 한 번씩 순차 호출한다. Show HN·`manual_only`·`needs_input`은 건너뛴다. 이미 최신 결과가 있으면 건너뛴다.

4. **브라우저 E2E 도구**  
   Playwright나 새 npm 의존성을 이 계획에 추가하지 않는다. Phase 5·8 브라우저 확인은 기존 테스트와 실제 브라우저 1턴으로 한다.

5. **`/api/v1`과 모바일**  
   이 계획의 끝은 로컬 계약과 웹이 그 계약을 쓰는 것이다. 외부 기기·TLS·pairing은 후속 계획이다. 성공 기준의 “모바일 앱”은 계약 호환을 뜻하고 모바일 앱 구현을 포함하지 않는다.

6. **기존 runner**  
   현재 `CliGrokTextRunner`/`CliCodexTextRunner`와 provider 토글은 Phase 2 이관 대상이다. Phase 0은 정본·검증·안전 설정만 고치고 runner를 제거하지 않는다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.

## 예상 일정과 릴리스 구간

| 순서 | 단계 | 예상 | 릴리스 판단 |
|---:|---|---:|---|
| 0 | 정본·검증·보안 결함 수정 | 1~2일 | 개발 확대 전 필수 |
| 1 | 완성 원고 계약·채널 정책 | 1일 | 계약 동결 |
| 2 | Grok·Codex OAuth provider | 1~2일 | fake + readiness |
| 3 | orchestration·결정론적 검증 | 2~3일 | AI 신뢰 경계 완성 |
| 4 | X·LinkedIn·Product Hunt 파일럿 | 2~3일 | `MVP-A`, 실제 사용 판단 |
| 5 | 웹 GUI 작업 흐름 | 2일 | `MVP-B`, 비개발자 사용 가능 |
| 6 | 나머지 채널 확대 | 3~5일 | 전체 채널 정책 적용 |
| 7 | 모바일 `/api/v1`·OpenAPI | 2~3일 | 모바일 개발 착수 가능 |
| 8 | E2E·문서·릴리스 | 1~2일 | 2차 MVP 종료 |

- 1인 순차 개발 기준 파일럿 `MVP-A`: `7~11 개발일`
- 웹에서 사용할 수 있는 `MVP-B`: `9~13 개발일`
- 전체 채널 + 모바일 API 계약 + 종료 검증: `15~23 개발일`
- 일정은 실제 OAuth 계정 로그인 상태와 provider 응답 안정성에 따라 달라질 수 있다.

## 단계별 중단 기준

- Phase 0에서 검증 원고 보존이 안 되면 provider 확대를 중단한다.
- Phase 2에서 CLI 도구 차단이나 token 비노출을 증명하지 못하면 실제 OAuth 호출을 중단한다.
- Phase 4에서 3개 파일럿 중 하나라도 사실·길이·정책 검증을 반복적으로 실패하면 전체 채널 확대 대신 profile/validator를 먼저 수정한다.
- Phase 6에서 공식 정책상 AI 작성이 허용되지 않거나 불명확한 채널은 `manual_only` 또는 `needs_review`로 보수적으로 유지한다.
- Phase 7에서 외부 기기 접속 요구가 생기면 이 계획에 임시 LAN 공개를 추가하지 않고 TLS·pairing 전용 후속 계획을 새로 만든다.
